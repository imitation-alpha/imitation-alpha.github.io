agent-00 · 用電腦硬體架構來理解 AI agent 系統！ (李宏毅老師經典的教學風格版)

這堂課我們不講玄學！我們用最硬核、最接地氣的電腦硬體架構，把 AI agent 從頭對答案，拆解給你看！

2026 年 5 月 19 日 · 10 分鐘 · Arthur Yau ·

好，各位同學大家好啊，那我們就準備來上課吧！今天這堂課呢，我們要來聊聊一個很神奇的技術，叫做用電腦硬體架構來理解 AI Agent 系統。那這個部分我不會講太長，我們預計三十分鐘內可以結束。

今天我們分成幾個部分：我們先來看為什麼用這個角度看很有用（去破除一些大家常有的迷思啦），接著看整個系統的架構圖 (Architecture map)，然後我們會一個個元件來拆解，從 CPU processor、working memory、external storage 一路講到 I/O peripherals。最後，我們再來看 multi-agent 還有 self-correction，當然還有大家最期待的實戰檢查清單喔！

好，那我們先來問大家一個問題。假設你今天想要寫一個修 bug 的 AI agent。結果呢，事情搞砸了，你回去看 log 發現它沒修好。這時候，第一個出現在你腦海裡的診斷（diagnosis）是什麼？

你可能會想說：『啊，這很簡單嘛！一定是 model 不夠聰明啦！』、『哎呀，model 又在 hallucinate（幻覺）了啦！』、『model 忘記了！』或者是『model 需要更大的 context window！』對不對？

欸，有時候這是真的。但很多時候，這根本是下錯診斷啦！

一言以蔽之，AI agent 其實就是圍繞著 LLM processor 打造出來的電腦系統而已。

這就像是動漫《葬送的芙莉蓮》裡面的魔族，他們其實沒有心，只是透過模仿人類的語言來欺騙人類，對不對？其實我們的 LLM 也是這樣耶！它只是在模仿人類說話的機率分佈，一顆字一顆字（token）吐出來。如果你只把它放在一個空的網頁對話框（chat box）裡，它就會跟魔族一樣，開始對你說謊、胡說八道，這也就是我們常聽到的「幻覺」（hallucination）啦！

那怎麼辦呢？我們不能只靠魔族自己的良心嘛，我們要在它周圍建立一套強大的「勇者團隊系統」，這套系統包含了防禦魔法、封印魔導書、還有各種偵測陷阱的工具。這樣一來，即使魔族本身有想騙人的衝動，在整個系統的嚴格監控和引導下，它也只能乖乖幫我們把事情做好。這個勇者團隊系統，白話文就是我們今天要講的 AI agent 系統架構啦！

LLM 是中央推理引擎（reasoning processor），但真正強大的能力，是來自它周圍的整個電腦硬體架構：context、memory（儲存記憶）、retrieval（檢索）、tools（工具）、drivers（驅動程式）、feedback（反饋）、tests、permissions，還有去協調整個 loop 的 harness。以下這是我從李宏毅近期六堂 agent 課程整理出的架構公式：

agent capability = model x context x tools x feedback x harness x memory

Model 很重要。當然重要。但它不是整台機器。

為什麼用這個角度來看很有用？

電腦硬體架構（Computer architecture）給了我們 these agent 開發者（builders）一套更乾淨、更精準的除錯語言（debugging language）。

大家想想看，沒有人會單純只用 CPU 的時脈去評估一台電腦好不好用，對不對？一個超快的 processor，如果沒有給它足夠的 working memory、外接儲存 storage、系統匯流排 buses、設備驅動程式 device drivers、I/O 連接埠、作業系統、中斷控制 interrupts、權限管理 permissions、診斷 diagnostics 還有錯誤恢復機制 recovery behavior，那它根本什麼事都做不了嘛！

Agents 也是一模一樣的道理。

欸你知道嗎，一個超強的 model 如果放在一個很爛的系統架構裡，它看起來也會顯得心神不寧、丟三落四的。相反地，一個比較小、比較弱的 model 放在一個紀律嚴明、設計精良的系統裡，它展現出來的實作能力可能會讓你大吃一驚！這神奇的點就在這裡，這中間完全沒有任何魔法，純粹就是系統架構改變了 processor 能夠看得到什麼、能夠做什麼、錯誤怎麼被捕捉，以及系統什麼時候才被允許宣布任務成功。

所以，一個真正有用的問題，絕不只是問『這個 model 是不是不夠聰明？』，而是要問：『現在是我們系統架構的哪一層（system layer）出錯了？』

系統架構圖 (Architecture map)

那我們來看一下這張緊湊的架構圖（Architecture map）：

  • LLM: 其實就是 CPU / 推理處理器 (reasoning processor)。
  • Context window: 其實就是 active working set（當前工作集，也就是載入到記憶體裡的資料）。
  • Long-term memory: 白話文就是 storage layer（硬碟、儲存層）。
  • Retrieval: 意思就是 page loader / cache fill（分頁載入器或快取填充）。
  • Tools: 就是外接設備 peripherals、I/O devices 還有各種硬體加速器 accelerators。
  • Tool schemas: 其實就是 drivers（驅動程式）還有系統呼叫 syscalls 啦。
  • Feedback 與 tests: 意思就是系統的中斷 interrupts、診斷 diagnostics 還有看門狗 watchdog 機制。
  • Harness: 其實就是主機板 motherboard、作業系統 OS、排程器 scheduler、權限層還有錯誤恢復系統（recovery system）。

雖然這個比喻（analogy）不是百分之百完美啦，LLM 當然不會像真正的 CPU 一樣去隨機存取記憶體（random access memory），vector database 也不完全是 page table，prompt 也不是真的 RAM。

但是，對於我們這些開發者（builders）來說，這個地圖超級有用！因為它會強迫你去檢查 model 外圍的介面（interfaces），而不是只會在那裡死命地盯著 model 的權重（weights）發呆，對不對？

LLM 只是 processor 喔，不是整台電腦啦

我們說 LLM is processor，是因為所有的核心推理步驟（reasoning step）都是在這裡發生的。

它接收序列化後的輸入 token，吐出輸出 token。它的 weights 編碼了它的語言能力、程式撰寫模式、世界知識、推理習慣，以及在 pretraining 和 post-training 階段學到的一切行為。

聽起來好像很厲害，但你沒有看錯，這還遠遠不夠！

我們來想想看一個場景：如果我們直接把 model 丟去修 bug，它會知道你的電腦裡有哪些檔案嗎？它不會。它會知道昨天使用者對它說了什麼嗎？它不會。它能自動知道它剛剛跑的命令有沒有噴錯嗎？它也不能。它甚至不會在回答『我做完了！』之前自己跑一次測試。它只看得到 harness 載入 prompt 的內容，也只能透過系統暴露的 tools 行動。

對不對？所以，當 agent 失敗的時候，你如果只會說『這個 model 太弱了啦』，這是不對的！很有可能是你的 active context 給錯了、你的 tool 定義太模糊了、或者是 schema 太寬鬆，甚至是因為 harness 居然允許 model 在沒有跑 verification 的情況下就停下來。所以記住：**LLM 是核心，但它不是整台電腦。**

Context 其實就是 loaded working set

第一堂課我們通常會講 Context Engineering，但是在我們硬體架構的視角裡，這其實就是 **working-set management**（工作集管理）。

LLM 沒有辦法隨時隨地用手伸進所有的 long-term memory 裡。它能看到的，只有當前 prompt 裡的那點東西。所以，任何重要的資料，都必須被序列化（serialized）成文字，塞進 prompt 這個能見的工作空間（workspace）裡。

這讓 context window 更像某個 process 已載入的 working set，而不是整個系統的 memory。它包含 current instructions、recent state、retrieved facts、tool outputs、user constraints、partial plans，以及系統選擇保留的 scratch reasoning。

如果我們用最天真、最 naive 的方法來做 agent，我們可能就是把所有的對話、所有的工具回傳結果（tool outputs），一股腦地全部用 append 的方式一直塞、一直塞：

C_next = C_current + new_input + model_output

這個方法在短短的聊天中還可以，但如果要做複雜的 agent，**完蛋了！** 為什麼？因為 tool outputs 變得太大，讀取檔案會瞬間淹沒 prompt，舊的錯誤也會一直留在裡面，重要的限制也被埋到最底下。這時候，你的 context window 根本不是什麼工作記憶體，它直接變成垃圾掩埋場（landfill）啦！

那怎麼辦呢？這時候我們就需要一個更聰明的函數 `F`，也就是：

C_next = F(C_current, new_input, model_output)

這個 `F` 就是神奇的地方！它必須決定哪些資訊要保持 hot（留在 active context 裡）、哪些要被淘汰（evict）、哪些要進行摘要（summarized）、哪些要寫入外部資料庫（externalized），或者什麼時候要委派（delegate）給其他 sub-agent 來做。

所以，**context engineering 根本不是在做 prompt 裝飾，它其實就是 LLM processor 的 memory management！**

Memory 與 retrieval 就是 storage 加 loading policy 嘛

那大家可能會有疑問：prompt 看到的 context，跟 memory（記憶）是一樣的東西嗎？其實不一樣喔！

在我們的架構裡，**Memory 其實是 prompt 外面更大的 storage layer**。這裝了：各種 files、筆記、日誌、向量 embeddings、資料庫、過去的 decisions，還有使用者的偏好。我們可以用一個公式來表示：

C = P + M

這裡的 `P` 就是 prompt 裡看得到的 working set，而 `M` 就是外部的 memory。

好，那問題來了：如果我們有一個超級龐大的專案，裡面有幾萬個檔案，我們能把整個硬碟的資料（M）一次塞進 RAM（P）裡面嗎？那肯定是不行嘛！即使你用的 model 號稱有百萬 token 的 context window，你硬塞進去，它也只會像我們前面講的《葬送的芙莉蓮》裡的魔族一樣，看花了眼，根本找不到重點，對不對？而且速度還慢到爆、算力費用貴到你想哭。

那怎麼辦呢？這時候我們就需要 **Retrieval（檢索）** 機制！它就像是作業系統的分頁載入器（page-loading layer）。它的工作就是：在外部 memory 裡找到最相關的那一小塊分頁（page），然後把它精準地帶進 active working set 裡面。雖然 vector index 不是真的 page table，但它們在架構上的角色是一模一樣的——讓系統不用背負所有東西，也能隨時拿到需要的 stored state。

這時候你就會發現，**sub-agents 其實也是一種 context-compression devices 喔！** 欸，這蠻厲害的耶！Parent agent 不需要自己去看一堆亂七八糟的 log，它只要把這個 messy branch 丟給 sub-agent 去處理，最後拿回一個精簡的報告（比如一個 code、一個 boolean，或是一個檔案路徑）就結束了。就這樣子，一點都不神秘。

Tools 其實就是 peripherals、accelerators 與 interfaces

我們接下來聊聊 Tools（工具）。大家有沒有想過，如果 LLM 只有大腦，卻沒有任何手腳，它能做什麼？它只能在 prompt 裡跟你打嘴砲而已，對不對？

它可能在腦袋裡推理了一萬步，知道這行 code 有錯，但它卻沒有辦法去修改檔案，也沒有辦法去跑測試。怎麼辦呢？

怎麼辦呢？我們必須給它手和腳，這就是 **Tools（外接設備）**！

在我們的架構裡，Tools 就是圍繞著 LLM processor 的 **I/O system（輸入輸出系統）**。比如：瀏覽器（browser tool）其實就是網路介面加網頁客戶端；計算機（calculator）其實就是數學協處理器（math coprocessor）；終端機（shell）就是程式的 execution environment；資料庫工具就是儲存控制器。LLM 負責「思考」，而 Tools 則讓系統能夠真正去「觸碰」這個物理世界。

那有了設備之後，我們要怎麼讓 CPU 去控制它們？這就需要 **Tool schemas（驅動程式，drivers）** 啦！

如果你的驅動程式寫得很爛，硬體就會經常當機，對不對？同樣地，如果你的 tool schema 定義得模糊不清，model 就只能在那裡瞎猜參數；或者你的 tool 每次執行完都丟回一大堆沒有結構的雜亂文字，那 model 就又會面臨 context-management 爆掉的困境。

所以，**一個專為 agent 設計的 tools，應該要提供 structured inputs、bounded outputs、簡短的 errors，還有 deterministic verification commands。** 人類用的介面（human interfaces）喜歡把狀態藏在花俏的按鈕後面，但 agent 用的介面，必須讓 state 是 machine-readable（機器可讀的）。

神奇的點就在這裡！這也是為什麼我們封面的主機板上，那些 RAM、插槽、外接埠、診斷燈不是隨便畫畫的裝飾品，它們代表的正是 agent 能夠發揮能力的 capability surface（能力表面）啊！

Feedback 與 tests 就是系統的 diagnostics 喔

接下來我們聊聊 **Self-correction（自我修正）**。如果一個 agent 只會自己寫 code，寫完之後就在那裡「自我反省」（self-reflection），這有用嗎？

這就像是一個工程師寫完代碼後，完全不編譯、不跑測試，只坐在椅子上閉著眼睛發呆想：『編譯成功...我覺得我寫得真完美。』這根本是玄學，對不對？它遲早會跟現實脫節，進入幻覺的無盡深淵。怎麼辦呢？

怎麼辦呢？我們不能只靠虛無飄渺的 vibes（感覺），我們需要實實在在的 **Feedback 還有 test signals（診斷信號）**！

一個真正有用的系統，必須要有**中斷信號（interrupts）還有診斷工具（diagnostics）**：像是 compiler errors、failing tests、linter 的警告、瀏覽器截圖、使用者的即時糾正、甚至是權限拒絕（permission denials）。

我們的目標不是叫 model『你再想想看喔』，而是要把環境中真真切切的 grounded signal 餵回給 processor。

這也是為什麼在程式開發（programming）領域，agent 做得特別好。因為環境（如編譯器或測試框架）會非常殘酷、非常誠實地告訴你：『你就是錯了！錯在第幾行！』，而 agent 就可以直接把這個錯誤訊息當成下一步的 input。

Tests beat vibes！ 測試可以直接創造出系統無法誠實忽略的中斷信號，神奇的點就在這裡！

Harness 其實就是 system layer

好，接下來是整門課對開發者來說最實用、最震撼的部分：**Harness Engineering**！

欸你知道嗎，這裡有一個超級經典、甚至有點殘酷的實驗。研究人員拿了一個超小、超廢的 2B 小 model 去做一個修程式 bug 的 task。如果只給它一個空的 chat box 叫它去修，它的表現爛到你想哭，一直接連不斷地 hallucinate，編造各種不存在的程式碼，然後還自信爆棚地說：『修好囉！』，當然最後是徹底失敗。

但是！當我們改變了做法，我們不換 model，我們只在它周圍加上了幾條非常死板、非常無聊的規則：

  1. 你必須先列出目錄（list directory）。
  2. 你在編輯檔案之前，必須先讀取檔案（read file）。
  3. 在你宣布你修好之前，必須先跑一次 verification script。

你猜怎麼著？**同一個小 model，在同一件工作上，它居然成功了！** 蠻厲害的耶！

這代表什麼？Model 並沒有突然在幾秒鐘內變聰明，它的 weights 根本沒有動。那為什麼它成功了？因為**它周圍的 system（系統）變得不那麼粗心了！**

這就是為什麼 harness 比 bus 大。Bus 只是在 components 之間搬資料。Harness 決定什麼事情可以發生。

它選擇要載入什麼 context、有哪些 tools、套用哪些 permissions、state 如何儲存、failures 如何浮現、tests 是否必須通過、何時 retry、何時 stop，以及成功 procedure 如何變成 reusable skills（可重用技能）。

在這個 analogy 裡，harness 是 motherboard 加 operating system，加 scheduler，加 permission layer，加 recovery system。

它是把 powerful text processor 變可派任工作高效員工的系統層！就這樣子，一點都不神秘。

Multi-agent 其實就是 network topologies 啦

很多人一聽到 Multi-agent（多智能體），就會覺得：『哇！這聽起來好高大上喔！』好像 agent 越多就一定越厲害一樣。但是——

如果你把十個沒訓練好的小 model 放在一個群組裡，讓它們毫無章法地互相聊天，你覺得它們會突然討論出相對論嗎？不會嘛！它們只會創造出更多的雜訊（noise），然後把對話視窗洗板洗得更亂，最後大家都爆 context，對不對？怎麼辦呢？

怎麼辦呢？我們必須明白，**Multi-agent 其實不是一項功能，它是一種 network topology（網路拓樸）的選擇！**

這完全是**分散式系統（distributed systems）**的邏輯。不管是 chain（鏈式）、tree（樹狀）、star（星狀）、mesh（網狀）、debate（辯論）、還是 manager-worker（管理者與員工）架構，它們的行為都完全不同。

處理器變多，電腦不一定會變快；溝通變多，結果也不一定會變好。拓樸結構會徹底改變你的演算法。例如，chain 很簡單，但只要前面的人出錯，錯誤就會像傳話遊戲一樣一路錯到底；mesh 可以互相監督，但它的 token 成本高到嚇人，還會產生很多干擾資訊；tree 可以分支成 variations，但方向 and merge policy 很重要。

所以，不要再傻傻地問『到底要用一個 agent 還是多個 agent？』，你應該要問：**『你正在建構哪種通訊網路？每個邊界（boundary）會跨過什麼 state？什麼 summary 被允許回到主迴圈？』**

Self-correction 就是一種 control loop

同樣地，很多人把 Self-correction（自我修正）神格化了，覺得它像是人類的自我反思，是什麼高級的靈魂覺醒。其實——

如果沒有外在的物理信號，LLM 就像一個在小黑屋裡自我安慰的人，它無論怎麼想，都只會在自己的幻覺世界裡打轉。怎麼辦呢？

怎麼辦呢？這其實就是一個經典的 **control loop（控制迴路）** 問題而已嘛！

系統嘗試一個動作，觀察環境回傳的 signal，更新內部 state，然後再 retry，或者當機立斷向上回報（escalate）。

這可以發生在好幾個不同的層級：在 token 解碼階段（decoding）我們可以調整機率；在工作流（workflow）階段我們可以跑『生成－驗證－修改』的 loop；而在訓練（training）階段，我們可以教導 model 養成在輸出最後答案前先檢查中間步驟的習慣。

那更進一步的 Self-improvement（自我進化）也是一樣的道理。系統能不能自己去改進它的 training data、優化它的 rewards、更新它自己的 tools，甚至是重寫 it own harness 規則？

我們現在其實還泥足深陷，還沒有完全跨過這條自我進化的「盧比孔河」（Rubicon）。雖然 AI 現在可以幫忙生成 pseudo-labels、幫忙寫寫 reward function、當個評判（AI judge），但這裡面有太多陷阱了：像是代理獎勵漂移（proxy reward drift）、自我訓練平台期（self-training plateaus），或者是 evaluator 被 model 破解（evaluator hacking），導致表面上指標很好看，實務上卻完全是垃圾。

所以，**在短期內，我最信任的自我進化路徑，其實是 harness improvement。** 也就是：去幫它加上一個更嚴格的 verifier（驗證器）、去把 tool schemas 定義得更精準、去把 reusable skills 整理乾淨、去定時清理 memory 或是優化 workflow。這雖然看起來不像自動重寫 weights 那麼中二和酷炫，但它**超級安全、超級容易檢查！**

Builder 實戰檢查清單 (Builder checklist)

所以，今天這堂課最實用的 takeaway 很簡單：**在怪 processor（模型）不夠聰明之前，先好好檢查整台 computer（系統）！**

  • 正確的 working set 有被載入到 prompt 裡嗎？
  • Long-term memory 有被乾淨地檢索（retrieve）出來嗎？
  • 你的 tools 有沒有暴露明確、易讀的 state 嗎？
  • 你的 drivers（tool schemas）有沒有限制住不合法的 actions 嗎？
  • Feedback 有沒有作為一個真實、殘酷的診斷信號（diagnostic signal）回傳給 model 嗎？
  • 你的 tests 或 watchdogs 有沒有成功阻止 model 耍賴、假裝它做完工作嗎？
  • Permissions（權限）和當前的 task 有匹配嗎？
  • Harness 知道什麼時候該 retry、何時該 stop，或者何時該 escalate（向上求助）嗎？

這就是為什麼 agent engineering 玩起來會覺得有點髒、有點混亂的原因。因為這裡面根本沒有什麼單一裝飾性的神奇旋鈕，我們是在 LLM processor 的周圍建造整套電腦系統，而每一層，都會徹底改變這個 model 展現出來的能力！

我認識最強的 agent builders，他們從不只會問『這個模型是不是不夠聰明？』，他們一定會問：**『今天是系統架構的哪一層壞掉了？』**
