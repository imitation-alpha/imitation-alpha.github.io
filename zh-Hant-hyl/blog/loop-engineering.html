agent-07 · Loop engineering 其實就是定時運行的 harness 啦

其實，一個會動的 harness 還不夠！如果讓 Agent 反覆自動跑個一百次，怎麼讓它不失控、不把你的 Token 錢包燒光？這就是 Loop Engineering 要解決的硬核問題啦！

各位同學大家好啊，那我們就準備來上課吧。今天這堂課呢，我們要來聊聊 loop engineering...

今天我們分成幾個部分：我們先來看為什麼只有一個 harness 還不夠，為什麼我們需要為 loop 加上 clock（時鐘）與 work queue（工作佇列）；接著來看怎麼用 budget（預算）與 stop rules（停止規則）來限縮 Agent 的行為，以及 feedback window（回饋窗口）和 verification（驗證）要怎麼設計；最後，我們還會聊聊 memory（記憶體）的保存策略、human review（人工審查）的邊界，以及如果是我的話會先 build 什麼樣的系統。

在之前的課程裡面，我們都把 Agent 當作是一個圍繞著 LLM 處理器（LLM processor）建成的電腦系統。我們常說 model 很重要，對不對？但其實周圍的 system（系統）更關鍵！是這個系統決定了 model 能看見什麼、能做什麼、什麼時候該 retry（重試），還有什麼時候必須停下來。

但是！當你的 harness（測試架構/運行容器）成功跑完一次之後，事情就結束了嗎？沒有喔！神奇的點就在這裡，如果你的 Agent 必須每小時跑一次、每晚跑一次、或者每次有人發 PR（pull request）、每次客服收到 ticket、每次評測失敗（failed evaluation）都要跑一次，那會發生什麼事？

以前的一次性 harness，白話文就是一個「單次的作業程序」。而我們今天要講的 loop，白話文就是一個「持續運轉的運作節奏（operating rhythm）」！

一言以蔽之：所謂的 loop engineering，其實就是把你的 harness 套上定時器、加上狀態管理，讓它能反覆自動運行而不會失控歪掉而已。

所以大家要記住喔：如果 harness 是針對單次 Agent 運行的保護殼，那 loop 就是這個殼再加上時間（time）、狀態（state）、佇列壓力（queue pressure）、預算（budgets）、驗證關卡（verification gates）以及升級/通報規則（escalation rules）！

Loop 就是裝上定時器的 harness 啦

以前我們是怎麼教 Agent 工作的第一步？我們跟它說：『你要先讀完文件再編輯喔』、『要用對的 tools 喔』、『要留下 evidence（證據）喔』。這個限制與引導的結構，就叫做 harness。但是，如果你想讓它每天自動幫你整理程式碼，你不可能每天手動去點它。那如果直接放任它自己一直跑呢？這就像《葬送的芙莉蓮》裡面的魔導玩偶，你叫它去打掃圖書館，它如果沒有人叫它停，它可能會一直掃、掃到把地板磨穿，甚至把珍規的魔法書當成垃圾丟掉！

那怎麼辦呢？

這時候我們就需要為它裝上一個定時器，這就是 loop！它決定了 harness 什麼時候該醒來（wake on schedule）、要去拿哪一個工作項目（item）、要繼承什麼樣的狀態（load state），以及到底做到什麼地步才算是一次完成的迭代（iteration）。

欸你知道嗎？用這種方式去思考，你的工程問題就會變得很具體。你不再是去追求一個空洞、抽象的『超強自主型 Agent』，而是去建立一個有明確 input（輸入）、output（輸出）、boundary（邊界）和 evidence（證據）的重複性流程（repeated process）。

這個定時器（timer）可以是那種最死板的 cron job，也可以是某種 event trigger（事件觸發器），像是：有人在 GitHub 留言了、CI 跑失敗了、資料夾裡多了一份新文件、或者 benchmark（基準測試）突然退步了。不管觸發條件是什麼，白話文就是：每次觸發，都必須產生一個『有邊界的任務（bounded piece of work）』。

Loop 其實是有 clock 的

大家要知道，clock（時鐘）不只是硬體零件，它其實是 product（產品）設計的一部分！因為它會徹底改變 Agent 的 behavior（行為）。

你想看，一個每分鐘跑一次的 loop，跟一個每天晚上才跑一次的 loop，它們的行為會一樣嗎？當然不一樣啊！如果是每分鐘都在跑的 fast loop，它就必須要有非常嚴格的 stop rules（停止規則）以及非常便宜的 checks（檢查），不然你可能一眨眼信用卡就被刷爆了。如果是每天晚上才跑一次的 slow loop，它就可以慢慢來嘛！它可以收集更多的 evidence、把工作打包成 batch（批次），甚至在動手（action）之前先發個訊息問人類：『請問我真的可以這樣做嗎？』

而且，clock 還需要很多看似無聊、但只要一壞掉就會讓你痛不欲生的運作細節（operational details）。像是什麼？像是 interval（間隔時間）、timeout（逾時限制）、quiet hours（安靜時間，比如半夜不要打擾使用者）、backoff（指數退避）、jitter（隨機抖動）、catch-up behavior（落後補進行為），還有如果兩個時間點（ticks）重疊了該怎麼辦？你沒有看錯，這些細節超級重要！如果沒有設計好，你的 loop 遲早會重複做工、默默漏掉工作，或者造成 retry storm（重試風暴）。

Work queues 把意圖變成真正的壓力

在開發系統的時候，我們常常會抱持著美好的幻想。我們跟 Agent 說：『你要幫我保持這個 repository 的健康喔！』結果咧？Agent 根本不知道要幹嘛。因為這只是你的『意圖（intent）』，它不是一個具體的 input（輸入）。如果只有意圖，Agent 就會像個無頭蒼蠅一樣亂飛。

那怎麼辦呢？

這時候我們就需要引入 work queue（工作佇列）。

我們不能給它抽象的口號，而是要給它具體的工作：『這裡有五個失敗的 check 項目，每一個項目都有特定的 lease（租約期限）、priority（優先級）與 owner（所有者），請你現在去 review（審查）它們。』

這個 queue 的妙處，就在於它能把那些『看不見的壓力（invisible pressure）』變得非常具體且可見。白話文就是：現在到底有多少個 items 正在排隊？有哪些項目已經過期了（stale）？哪些項目之前失敗過？哪些需要 human review（人工介入）？有哪些又因為權限不足（missing permissions）被卡住了？

欸，你知道嗎？對於 Agent 來說，設計這個 queue 其實就是在設計 prompt！每一個放進佇列裡的 work item，都應該包含明確的 goal（目標）、scope（範疇）、相關的 pointer（指標/連結）、允許的 actions（操作）、預期的 evidence（證據），還有一個超級清楚的 definition of done（完成定義）。這就像死發配任務一樣，一個好的 queue item，其實就是一份小型的合約（contract）！

Budgets 是限制 Agent 行為的邊界

好，那我們接著看下一個重點。

欸你知道嗎？Agent 最擅長的事情之一，就是幫你花錢（笑）。真的！不論是 token 數量、tool call 次數、真實世界流逝的時間（wall-clock time）、retry 次數、API 呼叫費，還是人類寶貴的注意力，只要放進一個看起來『好像很忙、很有生產力』的 loop 裡面，這些資源就會像蒸發一樣瞬間消失！

所以我們需要 budget（預算）。但是，大家千萬不要以為 budget 只是用來控制成本（cost control）而已喔。它其實更是一個 behavioral boundary（行為邊界）！為什麼？因為預算會改變行為嘛！如果一個 loop 被限制只能 retry 三次，那它就會非常珍惜每一次機會，學著讓每次 retry 都發揮最大價值。但如果你給它無限次的 retry 呢？它可能就會把所有的『不確定性』轉化為一堆無意義的盲目亂試（motion），最後什麼問題都沒解決，卻把你的 Token 刷爆了。

所以，budgets 必須要做到內外透明。在 run（運行）的內部，Agent 必須隨時知道自己還剩下多少 budget。在 run 的外部，維運人員（operator）也必須能清楚看到資源到底花到哪裡去了。一旦 loop 越過了某個臨界值（threshold），它就應該立刻停下來、降級運作（degrade）或者進行升級通報（escalate），而不是在那邊自己即興發揮！

Stop rules 其實就是安全機制

任何一個有用的 loop，都必須要有一種『不是因為成功而停下來』的方法。你想想看，如果一個 Agent 在跑一個任務，結果這個任務因為外部系統掛掉而永遠無法成功。如果它沒有別的停止方法，它就會在裡面無限循環跑下去，直到地老天荒。

那怎麼辦呢？

這時候我們就需要 stop rules（停止規則）！這是一個非常關鍵的安全機制（safety feature）。

最簡單的 stop rule 就是硬上限（hard maximum），例如：最多只能嘗試 N 次、最多只能跑 M 分鐘、最多只能修改 K 個檔案。但是，這還不夠聰明！更好的 stop rules 應該要能夠偵測到 pattern failure（模式失效）。什麼意思呢？白話文就是，它能發現：『欸？怎麼重複出現了一模一樣的 error？』、『怎麼改出來的程式碼差異（diff）越來越大，但測試卻完全沒有變好？』、『為什麼 Agent 一直在要同一個漏掉的 context？』、『或者，驗證器（verifier）為什麼連續兩次 reject（拒絕）同一個 claim（宣稱）？』

大家不要覺得設計 stop rules 是因為我們對技術很悲觀喔。相反地，這是為了讓 loop 保持『可檢查性（inspectable）』！你想想看嘛，一個因為觸發 stop rule 而停下來、並留下乾淨 trace（追蹤紀錄）的 loop，絕對比一個一直胡搞瞎搞到所有證據都被它自己的歷史紀錄（history）淹沒的 Agent，還要容易 debug 一百倍！

Feedback windows 決定了學習的速度

再來，我們來聊聊 feedback（回饋）。Loop 必須透過 feedback 來學習、來修正行為，但是 feedback 的時機點是非常講究的，也就是所謂的 feedback window（回饋窗口）。

有的 feedback 應該在運行過程中（inside the run）立刻給它；有的 feedback 應該在一天結束時才看；有的則應該留到每週審查（weekly review）。

我們一般可以把它分成兩種：

第一種是 fast feedback（快速回饋）。白話文就是『戰術層面（tactics）』的小修正。像是：某個 test 跑失敗了、某個 link 斷掉了、指令 timeout 了，或者某個 claim 沒有標明出處。這時候就要立刻跟 Agent 講，讓它當場改掉。

第二種是 slow feedback（慢速回饋）。白話文就是『戰略層面（strategy）』的大檢討。像是：這種類型的任務是不是太複雜、應該要被拆分（split）？某個 tool 的定義是不是太模糊（ambiguous）、容易讓 Agent 誤解？某筆 memory 內容是不是已經過期了？或者某個工作清單（checklist）應該要變成一個可複用的技能（reusable skill）？

如果你把這兩種 feedback window 混在一起，系統就會變得超級吵（noisy）！你想看，如果每一次小小的戰術失敗（例如打錯一個字），都立刻被寫進 Agent 的永久記憶體裡面，那它的 memory 很快就會被一堆無聊的芝麻綠豆小事（trivia）塞爆。但反過來，如果每一次策略上的大失敗（例如工具選錯），都只是被當作單次運行裡的短暫碎碎念（transient comment），那下週這個 loop 保證還會再犯一模一樣的錯誤！這就是為什麼我們必須把窗口分開的原因。

Verification 才是 Loop 的終極守門員

接下來，我們要講到一個非常、非常重要的觀念，那就是 verification（驗證）。如果沒有 verification，你的 loop 其實只是在重複做一件事情而已：就是不斷地產生內容（repeated generation）。

大家知道這樣會發生什麼事嗎？這會導致嚴重的 drift（漂移/走鐘）！Agent 跑著跑著，產出的東西就跟當初預期的目標越差越遠。

所以，verification 就是阻擋 drift 的那扇終極閘門（loop gate）！

這閘門不需要做到絕對完美，但它必須是非常明確且不可妥協的（explicit）。例如說：如果你做的是寫 code 的 loop，那你可能必須規定：一定要跑過 tests、通過靜態檢查（static checks），並且產出 diff（程式碼差異）的摘要。如果你做的是資料調研（research）的 loop，你可能需要它提供 source links（來源連結）、擷取的原文（extracted quotes），並且跑一次矛盾檢測（contradiction scan）。如果是客服支援（support）的 loop，可能需要檢索公司政策（policy retrieval），並在給客戶退款時加入 human approval gate（人工審批關卡）。

蠻厲害的耶，這套邏輯聽起來非常合理對不對？今天最核心的原則就是：這個 loop 絕對不能僅僅因為最後的 answer『聽起來很像完成了』，就自作主張把自己標記成 done！它必須拿出真憑實據（evidence）來通過驗證。

Memory 也需要定期清理喔

好，那我們繼續往下看。神奇的點就在這裡：一個重複運作的 loop，不管你有目標去設計它，它都一定會自己產生記憶（memory）！

這些記憶包括：日誌（logs）、摘要（summaries）、追蹤軌跡（traces）、未解決的任務、使用者的偏好（preferences）、失敗紀錄，以及一些運作時的小撇步（operational tricks）。但問題來了：這些 memory 到底是你精心挑選整理出來的（curated），還是只是隨機產生的歷史垃圾（accidental）？

一個好的 loop memory 系統，一定會保留指標（pointers）、出處（provenance）和有效期（expiry）。它會清清楚楚地標示：這個教訓（lesson）是從哪裡學來的？它上一次發揮作用是什麼時候？還有，它什麼時候應該被重新審查（review）或直接刪掉（delete）。相反地，一個糟糕的 loop memory，就像是一個滿嘴胡言的人，塞給你的只有一堆『聽起來信心滿滿、但完全沒有出處、也不知道過期了多久的 summaries』。

所以，保持記憶的衛生（memory hygiene）是 loop 安全性的重中之重。一條過期、失效的指令（stale instruction），往往比完全沒有指令還要可怕！因為 Agent 會自以為是地把它當作『已經學到的寶貴經驗（learned experience）』去執行，結果就會造成大災難。

Human review 應該要放在邊界上

大家也知道，人類的時間和注意力是非常昂貴的，所以 human review（人工審查） 絕對不能亂放。我們必須把它放在『最能影響關鍵決策』的地方。

你想看嘛，如果 Agent 產生的每一個 token 你都要人工 review 一次，那你不就成了人工輸入機器？這哪裡叫自動化，這白話文就是：多繞了好幾個冤枉路的手動工作流（manual workflow）而已！但如果你完全不 review 呢？那 loop一旦出錯，就會像滾雪球一樣不斷累積錯誤（compound errors）。

那怎麼辦呢？

所以，最理想的定位是把 human review 放在 risk（風險）發生變化的邊界上（boundaries）！

哪些是關鍵的風險邊界？例如：要動到 production（線上生產環境）了、要花真實的錢（spending money）了、要聯絡真實的使用者了、要公開發表內容了、要修改核心 policy（政策）了，或者是需要更新共享記憶體（shared memory）的時候。一個設計精良的 loop，它的特色就是：讓日常的例行公事（routine work）變得非常便宜、幾乎沒有額外成本；同時，一旦遇到跨越風險邊界（boundary crossings）的情況，就會變得無比顯眼、立刻攔截下來讓人類介入！

如果是我的話，我會先 build 什麼？

好，講了這麼多理論，那如果今天是我的話，我會想要先 build 一個什麼樣的 loop 系統呢？我絕對不會一上來就寫一個『能自我規劃、在所有系統裡到處亂跑』的超神大 Agent，那個太天方夜譚了。

我的做法非常簡單：從小地方開始。

就一個 queue。一個 trigger。一種 task（任務）的形狀。然後，一定要加上 dry-run mode（模擬運行模式）！設定一個非常清楚的 budget。產出人類可以輕鬆讀懂的 logs。設計一個『真的會失敗、不會假裝通過』的 verification 機制。在進行任何不可逆的操作（irreversible action）之前，加上一個手動的安全門檻（manual gate）。最後，每週做一次 review，把那些重複發生的 failures 拿出來分析，看看是要改 prompt、調整 tools、修改測試、還是調整 memory policy。

就結束了，就這麼簡單！

聽起來可能沒有那種『在各種系統之間穿梭自如的超級自主 AI（autonomous agent）』聽起來那麼刺激、那麼酷。但老實說，這才是唯一一個我自己敢真正信任、敢上線運作的系統。

今天這堂課最重要的一擊

所以，今天這堂課我們最想要傳達的核心觀念（the main lesson）是什麼？那就是：Agent 的 behavior，會在 loop 之中不斷地產生『複利效應（compounds）』！

如果你只是單次執行拿到一個很爛的答案，那沒關係，那只是一個 bug。但如果你的 loop 設計得很爛，那你其實是在 build 一個會按照你的時鐘設定（on schedule）源源不絕自動製造出更多 bug 的『量產系統』！這真的很可怕。

不過，樂觀的一面也是完全成立的喔。一個設計優良的 loop，甚至能把一個能力平庸的 modest model，鍛鍊成一個非常有用的運業者（operator）！為什麼？因為這個系統會不斷挑出有邊界的任務、嚴格檢查結果、妥善保存有用的 memory，並在碰到邊界改變時及時向上呈報（escalate）。

這也就是為什麼，我認為 loop engineering 絕對值得擁有它自己獨立的名字！它絕對不只是 prompt engineering（提示詞工程）、context engineering（上下文工程）或 harness engineering 的附屬品。它是一門獨立的學問——一門讓 Agent 的重複性工作在漫長時間中保持優良行為的學問！

今天學到的概念清單

我們今天聊到的實用 loop-engineering 概念，大家回去可以好好複習一下：

  • timer-triggered（定時觸發）與event-triggered（事件觸發）的 Agent 運作
  • work queues（工作佇列）、leases（租約期限）、priority（優先級）、ownership（所有權）與過期（stale）項目的處理
  • 單次運行中，針對 tokens、tools、time、retries、spend 與人類注意力所設定的 budgets（預算）
  • 針對重複失敗、沒有進展、風險臨界點與 escalation 所設計的 stop rules（停止規則）
  • 區分戰術型即時修正與戰略型 harness 升級的 feedback windows（回饋窗口）
  • 在將任務標示為完成之前，要求必須提供真憑實據（evidence）的 verification gates（驗證閘門）
  • memory retention policy（記憶保留政策）：包括 provenance（出處）、age（壽命）、review（審查）、expiry（過期）與 deletion（刪除）
  • 將 human review（人工審查）放置在 risk boundaries（風險邊界），而不是卡在每一個日常步驟裡
  • 在執行任何不可逆行為前，利用 dry-run mode（模擬模式）、可讀的 logs 和 manual gates 來保護系統
  • 每週進行 weekly loop review，將重複出現的失敗轉化為系統的優化方向

在我們下課之前，我們用 3 個重點來幫大家快速 Recap 今天的精華：

  1. Harness 加上定時器就是 Loop：不要盲目追求大而無當的 autonomous agent，把重複的工作封裝進有邊界的 loop 才是王道。
  2. Budgets 與 Stop Rules 是防禦機制：透過模式偵測與上限限制，避免 Agent 陷入無效的重複迴圈或把你的錢包燒光。
  3. Verification 與 Human Review 守住邊界：絕不單憑聽起來很好的 answer 就給 pass，唯有 evidence 驗證與在風險邊界上的人工審查，才能確保系統不走鐘（drift）。
