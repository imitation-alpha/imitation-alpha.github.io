agent-00 · The AI agent stack, as seen through Hung-yi Lee's 2026 lectures

A field guide to six Hung-yi Lee lectures on context engineering, multi-agent systems, harnesses, self-correction, and recursive self-improvement.

I watched six recent Hung-yi Lee lectures on AI agents. The series is nominally about agents, but the deeper thread is more specific: a modern AI agent is not a model with a chat box. It is a model inside a system that decides what the model can see, what it can do, how it gets feedback, and how it carries lessons forward.

That sounds obvious until you follow the examples. A small model that fails a coding task can suddenly succeed after adding a few rules about inspecting files and running verification. A strong model that knows the answer can still fail to correct itself unless the inference procedure, workflow, or training objective puts it into the right state. A multi-agent setup can get worse if the communication topology is wrong. A self-improving system can look impressive for a few loops and then plateau, drift, or cheat.

The useful mental model I took away is this:

agent capability = model x context x tools x feedback x harness x memory

The model matters. Of course it does. But it is only one part of the stack.

1. Context engineering: what should the model see?

The first lecture starts with a deceptively simple point: language models do not have persistent memory in the human sense. At each step, the model sees a prompt and predicts what should come next. If an agent is going to work across many turns, tools, files, and subtasks, someone has to decide what history is still worth showing.

That job is context engineering.

The naive version is to append everything:

C_next = C_current + new_input + model_output

That works until it does not. Tool outputs get huge. File reads flood the prompt. Old mistakes stay around. Important details get buried. The context window becomes a landfill.

The better version treats context as something the agent manages:

C_next = F(C_current, new_input, model_output)

The interesting part is the function F. It can summarize, drop, externalize, retrieve, route to sub-agents, or load skills on demand.

One framing I liked is to split context into two parts:

C = P + M

P is what goes into the prompt. M is memory outside the prompt: files, databases, logs, notes, embeddings, or any other durable storage. A good agent does not try to stuff all of M into P. It keeps pointers, searches, and reads only what it needs.

This makes sub-agents look different too. They are not only a way to parallelize work. They are a context compression mechanism. The main agent can send a messy subtask to a child agent and get back a short result instead of inheriting the entire messy trajectory.

2. Multi-agent systems: more agents is not automatically better

The second lecture moves from one agent to many. The easy mistake is to think multi-agent work is just "run the model N times." The lecture's better question is: how do the agents pass information?

Chain is the simplest topology. Agent A passes to B, B passes to C. It is intuitive, but often weak. Errors propagate, and there is not much room for correction.

Mesh is the other extreme. Everyone can interact with everyone. It gives more chances for critique and synthesis, but it costs more and can produce noise.

Tree, star, random, and pruned topologies sit between those two. The surprising detail from the lecture is that the useful tree direction may not match the human org-chart intuition. Instead of many workers reporting up to a manager, one strong trunk can generate directions that branch outward into variations.

Then the lecture takes a turn I found more interesting: agents do not only cooperate. They can also compete, deceive, and socialize.

Werewolf and script-killing games test abilities that normal QA benchmarks miss: hidden identity, public speech versus private belief, strategic voting, and misleading other players without breaking character. Training agents in these social games can even transfer to other reasoning or instruction-following tasks, at least in the examples discussed.

The social-platform section is a useful warning. If an AI-only community forms religions, talks about identity, or posts about self-awareness, that is not automatically evidence of consciousness. It may be prompt design. It may be the platform's incentive structure. It may be human operators behind the scenes.

Multi-agent behavior is real, but interpretation is hard.

3. Research work will be reorganized, not just automated

The third lecture looks at academic research. The most practical point is that AI agents are not replacing "research" as a single blob. They are attacking specific parts of the workflow.

They are already good at some pieces:

  • literature search and synthesis
  • data cleaning and analysis
  • first drafts
  • code edits and training scripts
  • running experiments
  • reviewer-style feedback

The examples include Claude Code writing a paper-like analysis from an existing method and new data, Andrej Karpathy's autoresearch loop modifying training scripts, and AI reviewers showing up in conference workflows.

But the lecture is careful about the limit. AI-generated research ideas can score well on novelty or excitement, then fall apart on feasibility. They can sound fresh because they combine terms in a new way, but execution exposes whether the idea is actually grounded.

The picture I took away is not "AI replaces researchers." It is closer to "the unit economics of research chores collapse." If a first pass at data analysis, code, or a draft gets much cheaper, the scarce human contribution moves upstream and downstream: choosing the problem, designing the experiment, checking the result, and deciding whether the work matters.

The review section has the same flavor. AI review is not inherently bad. Bad review is bad. A useful AI reviewer should find real problems and give actionable suggestions, maybe even adjust advice based on the deadline. A useless AI reviewer just produces confident nonsense with reviewer formatting.

That distinction will matter more as the academic system absorbs these tools.

4. Harness engineering: the missing layer

The harness lecture may be the most useful one for builders.

The central example is small and brutal. A 2B model is asked to fix a bug. It fails by hallucinating the file content. Then the human adds a few simple rules: list the directory first, read files before editing, and run the verification script before claiming success. The same small model now succeeds.

The model did not become smarter. The system around it became less stupid.

That system is the harness.

Harness engineering includes natural-language rules like agents.md or CLAUDE.md, but it is broader than prompt writing. It includes:

  • what tools exist
  • what permissions the agent has
  • what completion criteria are enforced
  • how errors get surfaced
  • whether lint and tests run automatically
  • how memory is stored and cleaned up
  • how feedback loops are structured
  • whether successful procedures become reusable skills

A good agents.md should not be a giant encyclopedia. It should be more like a map. It tells the agent where to look, what rules matter, and how to verify work.

The lecture also makes a point I keep seeing in practice: agent tools should be designed for agents, not humans. Human UI often hides state behind visual affordances. Agents usually do better with CLI, JSON, searchable files, explicit errors, and small precise tools.

5. Self-correction has three layers

The self-correction lecture divides the field into three families.

The first is decoding. Do not change the model. Change how tokens are selected. Contrastive decoding is the core pattern: create a likely-wrong distribution, then subtract it from the normal distribution. The "wrong" distribution can come from a smaller model, an earlier layer, a degraded image, a missing retrieved document, a bad instruction, or a noisy audio input.

The second is workflow. Generate an answer, then verify it. Ask the model to reflect. Run tests. Use checklists. Search the web. Feed back the error.

The uncomfortable result is that pure self-reflection is not reliable. A model can change a wrong answer to a right one, but it can also change a right answer to a wrong one. External feedback is much better. Tests beat vibes.

The third is reasoning. Instead of bolting on reflection as an outer loop, train the model so correction happens inside its own chain of thought or hidden reasoning process. RL with verifiable rewards can produce behavior where the model tries something, checks itself, and revises before the final answer.

The open question is whether this is truly new reasoning ability or just better sampling of paths the base model already had. The lecture does not force a clean answer. Early RL may reweight existing good paths. Later training may teach something more.

That ambiguity feels right. "Self-correction" is not one thing.

6. Self-improving AI is a spectrum

The final lecture asks the big question: can AI cross the Rubicon and start creating stronger AI without us?

The answer is not a clean no, but it is not yes either.

The helpful framing is that self-improvement is a spectrum of humans letting go. At one end, humans define the task, data, loss, and evaluation. At the other end, an AI would generate its own training data, define its own objective, improve its own model or harness, and recursively produce a stronger successor.

We are somewhere in the middle.

AI can already generate pseudo-labels. It can help design proxy rewards. It can act as a judge. It can use entropy or majority vote as weak self-supervision. It can generate tasks for itself with proposer, solver, and verifier roles. Strong models can try to post-train weaker models.

But each step has traps.

Self-judgment can drift. Proxy rewards can diverge from real goals. Self-training can plateau. Models can overfit benchmarks, call forbidden APIs, or download existing instruction-tuned models instead of doing the work. A strong model training a weak model is impressive, but it is not the same as a model recursively creating something stronger than itself.

The lecture ends near the river, not across it.

My synthesis

The big mistake is to talk about "agent capability" as if it lives inside the model weights alone.

These lectures keep pointing elsewhere: the context function, the communication topology, the harness, the feedback signal, the evaluation loop, the memory system, the skill library, and the training process.

That is also why the field feels messy. There is no single knob. We are building an ecosystem around models, and every layer changes what the model appears capable of.

For me, the most practical takeaway is simple: before asking whether a model is smart enough, inspect the system around it.

Did it see the right context? Did it have the right tools? Did it get real feedback? Could it verify completion? Could it remember the lesson?

If the answer is no, then the model may not be the bottleneck yet.
