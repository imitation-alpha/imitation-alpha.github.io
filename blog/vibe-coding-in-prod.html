agent-08 · Vibe coding in prod: forget code, not the product

Vibe coding can reach production only when the human stops acting like a line-by-line reviewer and starts acting like a product manager, test designer, and release owner.

Last August I wrote a short Threads note after watching Anthropic's “Vibe coding in prod” talk.

The core idea still feels right, but the thread was compressed. The blog version deserves more precision because “vibe coding in prod” sounds reckless if you treat it as “ship whatever the model wrote.”

That is not the useful interpretation.

The useful interpretation is: AI coding is pushing engineers toward the same management problem that every other field already has. You cannot personally inspect every implementation detail forever. You need to decide which details must stay human-owned, which details can be delegated, and which evidence lets you trust the delegated work.

Builder takeaway: production vibe coding is not about trusting vibes. It is about replacing line-by-line trust with scoped delegation, testable interfaces, observable behavior, and rollback.

Why revisit vibe coding in prod?

The talk makes one prediction hard to ignore: AI task length is expanding quickly. METR frames this as a horizon-length metric and reports a historical doubling time of roughly seven months. In the talk, the practical question is simple: what happens when a model can generate a day or week of engineering work at once?

At one-hour task length, a senior engineer can still stay in the loop. Read the diff. Ask for changes. Run the tests. Keep the mental model warm.

At one-day or one-week task length, that breaks. If the only safety strategy is “read every line the model wrote,” the strategy does not scale with the capability curve.

This is why the compiler analogy in the talk is useful. Early compiler users could inspect generated assembly. Modern engineers mostly do not. We still care deeply about the product behavior, performance, correctness, and security. We just moved trust to another abstraction layer.

AI-generated software needs the same move. Not blind trust. A better abstraction layer.

Forget code, not product

Karpathy's original vibe-coding phrase includes the line “forget that the code even exists.” The dangerous reading is to forget everything: code, product, users, security, billing, data, and rollback.

The production reading is narrower:

forget the code, not the product

You may stop treating the diff as the primary artifact. You cannot stop owning the product contract.

That contract includes inputs, outputs, invariants, latency, privacy boundaries, migration behavior, user-visible semantics, observability, and failure modes. The model can write and explain. The human still specifies, verifies, and decides.

This is not a new kind of responsibility. A PM can judge whether a feature works without reading every implementation detail. A CTO can evaluate an expert's work through acceptance tests, architecture review, and operational metrics. A CEO can spot-check an accountant's model through the slices that matter.

Software engineers are just less used to giving up the implementation layer because we historically had to understand the whole stack ourselves.

Verification is the abstraction layer

If you do not inspect every line, you need something stronger than vibes.

The abstraction layer is verification. Not one verifier, but a stack of signals:

  • Contract tests: the input-output semantics that must stay true.
  • Integration tests: whether the generated code works with real dependencies.
  • Stress tests: whether stability holds over long runs, not just one happy path.
  • SAST and SCA: static analysis and dependency scanning before merge.
  • Reproducible builds: pinned dependencies and repeatable environments.
  • Observability: latency, error rate, saturation, business metrics, and logs after release.
  • Rollback: feature flags, canaries, and a fast path back to known-good behavior.

The Anthropic example in the talk was a Claude-heavy 22,000-line change to a production reinforcement-learning codebase. The important detail is not the line count. The important detail is how the risk was shaped: days of human planning, leaf-node concentration, targeted human review for extensible pieces, stress tests for stability, and human-verifiable inputs and outputs.

That is the production version of “let Claude cook.” You do not ask the model to replace accountability. You design the work so accountability has handles.

Leaf node first

My favorite operational rule from the talk is also the simplest: start at leaf nodes.

A leaf node is a part of the codebase that other systems do not deeply depend on. It might be a CLI utility, a pure-function library, an edge adapter, a report generator, a UI-only surface, or an offline pipeline stage with clear input-output behavior.

Leaf nodes are not automatically safe. They are safer because the blast radius is easier to bound:

  • fewer downstream dependencies break if the implementation is messy;
  • rollback is cheaper because the change is isolated;
  • contract tests can pin behavior at the boundary;
  • humans can verify outputs without understanding every internal step;
  • tech debt is less likely to become the trunk that everything else grows from.

The trunk and branches are different. Core architecture, auth, billing, permissions, data migrations, shared abstractions, public APIs, and security boundaries still need deep human ownership. The talk is explicit about this caveat: tech debt is hard to measure without reading code. Until we have better tech-debt verifiers, do not hand the trunk to the model and hope the tree survives.

Be Claude's PM

The strongest workflow shift is mental: treat Claude like a very fast new engineer, not like a magic compiler with no onboarding cost.

In the talk, the pre-work matters. Spend 15–20 minutes collecting the task into a strong prompt. Explore the codebase. Find the relevant files. Name the patterns to follow. State the constraints. Ask the model to expose unknowns before it writes too much.

I think of this prompt as a small PRD:

  • Background: why this change exists and what system it touches.
  • Goal: the user-visible or operator-visible outcome.
  • Acceptance criteria: what must be true before the work is done.
  • Constraints: forbidden libraries, compatibility needs, latency budgets, data boundaries.
  • Edge cases: known weird inputs, old migrations, failure modes, rollback behavior.
  • Verification: tests, commands, screenshots, logs, metrics, or review artifacts required in the final answer.

This is not prompt decoration. It is product management. If a new human engineer would fail with a one-line ticket, the model probably will too. The difference is that the model can fail much faster and produce a much larger diff.

The double loop

For production work, I want two loops: a specification loop before implementation and a release loop after implementation.

spec loop:    prompt → plan → critique → refined PRD
release loop: draft → tests → CI/security → canary → metrics → rollback or expand

The spec loop reduces ambiguity before the model spends a large budget. It is where you ask: what should change, what should not change, which files matter, what assumptions are dangerous, and what evidence will prove success?

The release loop prevents a convincing final message from becoming the definition of done. The agent can claim success only after the environment has produced evidence.

This is where the original thread's checklist still holds:

  • Use coverage targets when the feature lends itself to coverage; I often treat 80%+ as a useful floor, not a magic number.
  • Run SAST and SCA in CI; a critical finding should block merge.
  • Prefer reproducible builds through pinned dependencies, Nix, Bazel, lockfiles, or equivalent discipline.
  • Deploy behind a feature flag or canary when the change touches real users.
  • Watch latency, error rate, and product metrics after release.
  • Require the agent to record what changed and what verification actually ran.

The point is not ceremony. The point is to make the model's work legible to the system around it.

What counts as safe enough?

Safe enough is contextual. A local demo, an offline batch job, an internal dashboard, a production payments path, and a schema migration do not deserve the same autonomy budget.

My default rollout ladder looks like this:

  1. Offline or local-only task: let the agent move faster, but still require runnable verification.
  2. Leaf-node production code: add contract tests, CI, human review of interfaces, and rollback.
  3. Shared component: require architecture review and smaller diffs; use the model as implementer, not owner.
  4. Critical path: use AI for planning, test generation, migration rehearsal, and review assistance, but keep human ownership over the final design and release decision.

The boundary can move as models, tools, and verifiers improve. But the boundary should move because evidence improved, not because the demo felt magical.

What I would not vibe code

I would not ask a model to autonomously ship a critical production path where I cannot state the contract, run the verifier, or roll back quickly.

That includes auth, billing, permissions, customer data deletion, compliance-sensitive flows, irreversible migrations, secret handling, and anything where “we can fix it later” means users pay the cost.

I would also be careful with non-technical operators using vibe coding to build real businesses from scratch. The talk makes this point directly: if you cannot ask the right questions, you cannot be an effective PM for the model. Vibe coding is a creative unlock, but production requires enough domain understanding to know what is dangerous.

For games, prototypes, personal tools, and low-stakes experiments, go fast. For production, the human job changes from typing code to designing bounded work and evidence.

The main lesson

Vibe coding in prod is not the death of engineering judgment. It is a demand for more explicit engineering judgment.

The model writes code. The human defines the work, chooses the boundary, protects the trunk, designs the tests, watches the metrics, and decides whether the evidence is good enough.

That is why the line I still like from my original thread is:

Claude writes and explains. You specify, verify, and decide.

If we keep that division of labor, “forget the code” becomes less reckless. It means the code is no longer the only thing we know how to inspect. The product contract, verification harness, and release loop become the objects of engineering.
